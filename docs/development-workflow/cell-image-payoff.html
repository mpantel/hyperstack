The whole win is cache overhead

Runner time fell by 159 job-minutes. Almost exactly that much — 169 job-minutes — was restore_cache plus archive_cache, and it is now gone. The tests themselves did not get faster: aggregate step_script rose 12%.

Archiving was the expensive half and the easiest to miss: with policy: pull-push and when: always, every job re-uploaded its 258 MB of gems whether or not anything had changed — 150s per job on average, against 57s to restore. That is why the small gems collapsed: for hyper-trace, cache traffic was the job.

One job went the other way — but only three of its cells

rails-hyperstack is now the longest job in the pipeline at 644s, up from 455s, and it sets the critical path the other 48 jobs finish inside. It lost its 59s of cache overhead like everyone else and still ended up 189s worse, so the regression is entirely inside step_script.

A third pipeline pins it down. Pipeline 6645 ran the same matrix at less than half the concurrency — 8 to 12 parallel jobs where 6639 had 23 — and the three rails61 cells still took 637–646s. Runner contention is not the explanation. In the same run rails72-react16 came in at 216s, faster than its 266s before the change, so that cell never regressed at all; its 400s in 6639 was contention.

What the rails61 cells do and rails72 does not is one branch of spec:prepare: the rails_version < '7' block, which gem installs pinned old builds of zeitwerk, net-imap, concurrent-ruby and nokogiri before generating the app. That branch is the regression.

Why a gem cache cannot fix it

The cost sits in spec:prepare, which builds a throwaway Rails app from scratch. Inside it, the same work got slower on the cell image:

  • nokogiri 1.15.6, built from source both times: 78s → 202s
  • sassc and byebug native extensions: 43s → 71s
  • gem install rails itself: 9.4s → 9.7s — unchanged, which argues against CPU contention or a slower network
  • and on rails72-react16, which skips those pinned installs entirely, nothing regressed

None of it is reachable by the cache we removed. spec:prepare shells out under Bundler.with_unbundled_env and runs plain gem install, so those gems land in GEM_HOME, never in local_gems — the only path the cache ever held. The proof is in the before column: the cache was warm and restoring, and nokogiri still compiled from source every run.

Re-enabling that cache for this one job would restore its 59s of upload cost and recover none of the 232s. What would work is prebaking the four pinned gems into the cell image, exactly as #57 did for local_gems — the versions are literals in the Rakefile and the cell already fixes the Rails version they hang off, so a rails61 image can carry them and gem install becomes a no-op. A cache could only reach them by first pointing GEM_HOME at the project directory, which risks the image’s own prebaked bundle for a strictly worse result.
